## Repro

1. Write a patch with a FieldPixel node whose code is `a = ` followed by 4000 `(`, then `0.5`, then 4000 `)`. The file is about 8 KB.
2. Open it, or run `Infinite --frame p.inf 0.5 out.png`.

## Expected

The node reports a compile error, and the rest of the patch loads.

## Actual

SIGSEGV (rc 139). The recursive-descent parser has no depth limit. Each parenthesis costs about 9 stack frames (ParseOr down to ParsePrimary). A left-deep chain is parsed by a loop, but the later passes recurse on the tree it builds. These are the crash thresholds measured on macOS's 8 MB main stack:

| Shape | Survives | Crashes |
|---|---|---|
| nested parentheses | 2000 | 4000 |
| unary minus run | 10000 | 100000 |
| `a + a + ...` chain | 10000 | 20000 |

That is about 2.7 KB per parenthesis. On Windows the main thread gets 1 MB (CMake does not raise it), so the estimate there is a crash at roughly 350 parentheses. This was not run on Windows (P5). Patches come from files, share bundles and the community gallery, so one bad file is enough to crash on open.

## Fix note

ParserState now keeps two counters, restored on scope exit by a small guard.

- **Nesting** counts each ParsePrimary and ParseStatement entry (parentheses, unary ops, call arguments, blocks). The cap is 100.
- **Depth** counts the same, plus each link of a binary or postfix chain. The cap is 500.

Past either cap the parse fails with "expression is nested too deeply", which surfaces as E_FIELD_COMPILE. The caps are sized for Windows' 1 MB stack, using the costs measured above.

- Every crafted file above now gives rc 3 with E_FIELD_COMPILE instead of a crash.
- All 54 repo patches that carry field code still validate, with none hitting the limit. The deepest nesting in them is 5, and the most operators in one statement is 12.
- All 8 INFINITE_FIELD*TEST self-tests pass.
- A side effect: 1000 nested parentheses rendered on base, and is now refused.
