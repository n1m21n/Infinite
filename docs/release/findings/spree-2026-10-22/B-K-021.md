## Repro

Drop any of these onto a Video Source node (or open a patch that references one):
- A 4 KB Hap1 .mov whose `stsz` lists one sample of 0xF8000809 bytes.
- A Hap1 .mov whose `stsz` has a fixed sample size and a sample count near 2^32.
- A Hap1 .mov whose sample entry claims 65535 x 65535.

## Expected

Open fails with "not a playable HAP movie", the same as for any other damaged file.

## Actual

- **Oversized sample:** `ReadFrame` resizes its buffer to the sample's stsz size before reading. That allocates and zeroes ~4 GB per frame, on the decode thread, during export and in Probe.
- **Huge fixed-size count:** `ParseTrak` sizes `sizes(count)` and `times.reserve(count)` from the count, which is 16-32 GB. Nothing checks that count, because a fixed size has no table to compare against.
- **Huge dimensions:** every frame buffer is `TextureBytes(w, h)`, which is ~4 GB at 65535².

Each one either stalls for many seconds or gets the app killed for running out of memory.

## Fix note

`HapReader.cpp` now checks three things:
- `LoadMovie` refuses a track if any sample runs past the end of the file. A cut-off file was already meant to be refused (CompAudit's "cut-off file refused" check).
- `ParseTrak` refuses a fixed-size count greater than fileSize / fixedSize.
- `ParseTrak` refuses width or height above 16384, which is the largest texture a GPU we run on accepts.

Callers are unchanged, since a refused open already gives an error string:
- VideoSourceNode decode, export and Probe.
- CompAudit selftests.
