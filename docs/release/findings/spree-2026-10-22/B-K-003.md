## Repro

1. A HAP `.mov` whose frame uses the chunked form (top compressor 0xC0): a chunk table with N compressor bytes, N*4 bytes of sizes, and an offsets section (type 0x04) shorter than N*4 bytes, placed at the end of the frame.
2. Open it in a Video Source node (or ship it with a shared patch).

## Expected

The frame is refused as damaged.

## Actual

DecodeFrame (HapReader.cpp:457) records where the offsets section starts but not its length, then reads `Le32(offsets + c * 4)` for every chunk (:480). ASan: heap-buffer-overflow READ at HapReader.cpp:480 with N=16 and an empty offsets section. The second pass also trusts that the per-chunk output sizes fit `out`, which holds only because their sum is compared, and that sum can wrap.

## Fix note
Verified 2026-10-22 with a standalone ASan harness on Hap::DecodeFrame: the crafted frame is refused ("HAP chunk table is damaged"), and valid chunked frames, with and without an offsets table, decode to the same bytes as before. In-app COMPAUDIT on the branch: every HAP case passes (snappy, file probe and open, raw, snappy and chunked frames decode with matching bytes, cut-off file refused, DXT1 and HAP Q nodes shown); the only flags are the two known Fluid ones.
