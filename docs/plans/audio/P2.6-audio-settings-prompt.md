# P2.6 — Audio device & I/O settings

## Context (read this before touching anything)

This lands after P2.5 (Transport now runs sample-accurate off the real audio
callback — see `docs/plans/audio/README.md` and
`docs/plans/audio/P2.5-transport-prompt.md`) and before P3 (Notes/Synths/
Effects). It is new scope, not in `docs/plans/audio/README.md`'s original
phase list — the user asked for it directly because right now there is no
way to pick an audio device, sample rate, or buffer size at all, which
matters before P3's synths need to be heard through real hardware.

**Confirmed, current state (verified against the live code this session):**

- `AudioEngine::Start()` (`src/audio/AudioEngine.cpp:35-42`) calls
  `Platform::AudioDeviceOpen(...)` and takes whatever sample rate comes
  back. No device is chosen.
- `Platform::AudioDeviceOpen` (`src/platform/Platform.mm:1848-1900`)
  constructs a fresh `AVAudioEngine`, reads `[mixer outputFormatForBus:0]`
  (i.e. whatever the *system's current default output device* reports), and
  starts it. There is no device enumeration, no `AudioDeviceID` selection,
  no requested sample rate, no requested buffer size, anywhere in this path.
- **A second, unrelated `AVAudioEngine` instance already exists** at
  `Platform.mm:1595-1657` (`AudioStart`/`AudioStop`/`AudioIsRunning`/
  `AudioDeviceName`, using file-local `gEngine`/`gRunning`/`gDeviceName`/
  `gLiveAnalyser`). This is a pre-existing, older feature — a live
  microphone level/FFT analyser, unrelated to the new synth engine — that
  taps `[gEngine inputNode]` for its *own* separate mic capture. It has
  nothing to do with `AudioEngine`/`AudioNode`/P0-P2.5's work. **Decide
  explicitly (see Open decisions below) whether this phase's new "audio
  input device" setting governs this pre-existing capture path too, or is
  scoped only to the new synth engine's future audio-input nodes** — do not
  silently assume one or the other.
- There is no settings/preferences persistence mechanism anywhere in this
  codebase. Global UI toggles like `gSnapToGrid`/`gGridSnap`
  (`src/main.cpp:261-262`) are plain in-memory globals that reset to their
  compiled-in defaults every launch — they are never written to or read
  from disk, not even inside the patch file. The existing "Menu" top-level
  ImGui menu (`src/main.cpp:8672-8700`, inside the `BeginMenuBar()` block
  starting `:8605`) is the precedent for how app-level (not per-patch)
  settings are exposed: a `BeginMenu("Menu")`/`SeparatorText(...)` section
  with widgets bound directly to global variables, no separate window.

## What this phase adds

1. **CoreAudio HAL device enumeration.** `AVAudioEngine` alone cannot select
   a non-default output device on macOS — you have to reach through to the
   underlying `AudioUnit` (`[engine outputNode].AUAudioUnit` /
   `kAudioOutputUnitProperty_CurrentDevice` via `AudioUnitSetProperty`) or
   use `AudioObjectGetPropertyData` with `kAudioHardwarePropertyDevices` /
   `kAudioObjectPropertyScopeGlobal` directly against `AudioObjectID`s. Add
   this enumeration (device name + `AudioDeviceID` + is-input/is-output,
   via `kAudioDevicePropertyStreamConfiguration`) as new `Platform`
   functions:
   ```cpp
   struct AudioDeviceInfo { std::string name; uint32_t deviceId; bool isInput; bool isOutput; };
   std::vector<AudioDeviceInfo> AudioListDevices();
   ```
   Add this to the `Platform` namespace declared in `src/platform/Platform.h`
   (near the existing `AudioDeviceOpen`/`AudioDeviceClose` declarations at
   `:190-191`) with the implementation in `Platform.mm`.

2. **Device/sample-rate/buffer-size selection on the new synth engine.**
   Extend `Platform::AudioDeviceOpen`'s signature to accept an optional
   requested output `AudioDeviceID` (0 = system default, preserving current
   behavior), requested sample rate, and requested buffer (frame) size:
   ```cpp
   bool AudioDeviceOpen(AudioRenderCallback callback, void* userData,
                        double& outSampleRate, std::string& outError,
                        uint32_t requestedDeviceId = 0,
                        double requestedSampleRate = 0.0,
                        int requestedBufferFrames = 0);
   ```
   Setting a non-default device requires calling
   `AudioUnitSetProperty(... kAudioOutputUnitProperty_CurrentDevice ...)` on
   `h->engine.outputNode.audioUnit` **before** `[h->engine startAndReturnError:]`.
   Setting sample rate / buffer size on macOS is a **device-wide, not
   app-scoped** property — you set `kAudioDevicePropertyNominalSampleRate`
   and `kAudioDevicePropertyBufferFrameSize` on the `AudioDeviceID` itself
   via `AudioObjectSetPropertyData`, which affects every app using that
   device system-wide until changed again. **State this tradeoff plainly in
   the UI** (e.g. a one-line note near the buffer-size control) rather than
   changing it silently — this is a real, surprising-if-undocumented macOS
   quirk, not a bug to hide.
   Requested values that the device rejects (unsupported sample rate,
   clamped buffer size) should fall back to whatever the device actually
   reports after the request, the same way the current code already reads
   back `format.sampleRate` post-open rather than assuming the request
   succeeded verbatim.

3. **Oversampling: scope this narrowly.** There is no existing global
   oversampling mechanism, and the plan's own §3 Effects table already
   scopes 4× oversampling as a **per-effect** concern (Drive: "4× oversampled",
   `README.md:159`), not a device-level setting — a global oversampling
   toggle doesn't have a clear target yet since no DSP nodes exist to
   consume it (P3 hasn't landed). Add a single global `float gAudioOversample`
   default `1.0f` (values `1`/`2`/`4`) stored the same way as the other new
   settings in this phase (see item 5), wired nowhere yet — this phase's job
   is to make the *setting* exist and be visible, not to make anything act
   on it. Say explicitly in your summary that no node reads this yet — it's
   a placeholder P3c's Drive/AudioFilter kernels will read once they exist,
   not a claim that oversampling is implemented.

4. **Wire it into `AudioEngine::Start()`.** `AudioEngine::Start()`
   (`AudioEngine.cpp:35`) needs the three new settings values to pass
   through to `Platform::AudioDeviceOpen`. Add matching fields/setters to
   `AudioEngine` (mirroring how `mSampleRate` already exists at
   `AudioEngine.h`) so the UI layer in `main.cpp` can set the selection
   before calling `Start()`, without `main.cpp` reaching into `Platform`
   directly (keep the existing layering — `main.cpp` talks to `AudioEngine`,
   `AudioEngine` talks to `Platform`).

5. **UI: an "Audio" section in the existing "Menu" menu.** Follow the exact
   precedent at `main.cpp:8672-8700` — no new window, no new persistence
   format (none exists in this codebase yet; introducing one is out of
   scope for this phase, see Open decisions). Add a `SeparatorText("Audio")`
   block with:
   - A combo box listing `Platform::AudioListDevices()`'s output devices
     (default = whatever's currently active).
   - A combo box listing `Platform::AudioListDevices()`'s input devices
     (wire it through even though nothing yet consumes an input device on
     the new engine — same "setting exists before the thing that reads it"
     pattern as item 3).
   - Sample rate as a combo of the standard set (44100/48000/88200/96000)
     rather than free text — matches how `AVAudioFormat`/CoreAudio actually
     negotiate rates, and avoids a text field that can hold nonsense.
   - Buffer size similarly as a combo (64/128/256/512/1024/2048), with the
     device-wide caveat from item 2 shown as `ImGui::TextDisabled` under it.
   - The oversampling placeholder from item 3, as a combo (1×/2×/4×), with
     a `TextDisabled` note that no node uses it yet.
   - Changing device/sample-rate/buffer-size while the engine is already
     running (`AudioEngine::Instance().Start()` already called — check via
     the existing `SampleRate() > 0.0` pattern used elsewhere) must
     `Stop()` then `Start()` again with the new settings rather than trying
     to hot-swap a live `AVAudioEngine`. Show the actual post-open sample
     rate/buffer size Platform reports back (not just the requested one) so
     a rejected request is visible instead of silently wrong.

## Open decisions — you decide, state your reasoning, don't silently pick

- **Does the new "input device" selector also govern the pre-existing mic
  analyser at `Platform.mm:1595-1657`?** Two reasonable answers: (a) yes,
  thread the selected `AudioDeviceID` into `AudioStart()` too, unifying
  device selection across both engines; (b) no, leave that path on system
  default for now and scope this phase's input-device setting purely to
  the new synth engine (which has no audio-input nodes yet anyway — P3
  territory). Recommendation: **(b)**, it's less code and doesn't risk
  regressing a working, unrelated feature for a setting nothing currently
  consumes — but say explicitly which you picked and why in your summary.
- **Should these settings persist across launches?** Recommendation: **no,
  not this phase** — there is zero precedent for settings persistence
  anywhere in this codebase (confirmed: `gSnapToGrid` et al. are
  session-only), and inventing the first-ever preferences file format
  should be its own deliberate decision, not a side effect of this phase.
  Default to system default device / device-native sample rate / 512-frame
  buffer / 1× oversampling every launch, same as today's implicit behavior.

## Explicitly out of scope

- Anything about `OutputNode`/recording/export (that's the next phase,
  P2.7 — wiring the live synthesized audio graph into
  `src/nodes/OutputNode.cpp`'s recorder, which currently only reads
  `AudioFileNode`-backed files off disk, not a live render).
- The audio-analyse-as-modulator node — this already has a direct precedent
  (`ImageAnalyzeNode`, `src/nodes/AnalyzeNodes.h:18-80`, `IModulator`
  `Tap`/`ModulatorOutput()` pattern) and belongs in P3d per
  `README.md:344-346` ("Envelope Follower → modulator"), not here.
- Any node/DSP consuming the oversampling setting — see item 3.
- Settings persistence — see Open decisions.
