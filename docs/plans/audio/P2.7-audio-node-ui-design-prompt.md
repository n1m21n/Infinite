# P2.7 — Audio node UI system + reference Oscillator

## Why this phase exists

This is new scope, inserted between P2.5 and P3 at the user's request. It is
**not** in `docs/plans/audio/README.md`'s original phase list.

The trigger: P2 shipped three minimal proof nodes (Oscillator/Gain/Audio Out)
to prove the cable plumbing. Rendered in the editor they look nothing like a
professional DAW/modular instrument — and inspecting *why* turned up four
structural problems that would each be multiplied by ~30 if P3 started now.
This phase fixes the system, then proves it by building one genuinely complex
node (the real Oscillator) on top of it.

This is the same argument the plan already makes for "P2 before P3"
(`README.md` §5): it is the phase that *reduces* future cost. Building 30
audio nodes on the current node-body layout produces 30 sparse nodes and 30
hand-written param functions.

## Confirmed current state — verified against live code, do not re-derive

**Node body layout is an image-compositor layout.** Every node that isn't
specially cased draws a square image preview then a vertical stack of
full-width sliders:
- `DrawPreview(INode*)` — `src/main.cpp:4889`. Draws a checkerboard backdrop
  at `kPreviewSize` (190.0f, `main.cpp:104`), blits `GetOutputTexture()`, and
  falls back to a literal `"no input"` string (`main.cpp:4919`) when the
  texture is 0.
- It is reached from the final `else` of the node-body dispatch at
  `main.cpp:13556-13557`. **Audio nodes hit that `else`**, which is why an
  Oscillator currently renders a 190px empty checkerboard reading "no input"
  — it has no texture and never will.
- The precedent for opting out is `GeometryNode`'s branch immediately above
  (`main.cpp:13531-13549`): geometry emits a mesh, not a picture, so it draws
  a compact info box instead. **Audio nodes need the equivalent, but richer.**

**Only one param widget shape exists.** `ModSlider` (`main.cpp:563`) is
full-width (`kParamWidth` = 168.0f, `main.cpp:121`) and draws its own
modulator input pin. `DropdownButton` (`main.cpp:420`) is likewise
full-width. There is no compact, grid, or multi-column variant anywhere.

**Params are one long `dynamic_cast` else-if chain** at
`main.cpp:~13640-13760`, one branch per node type, each calling a hand-written
`DrawXxxParams` function. There are already ~60 branches. Thirty audio nodes
naively added means thirty more.

**`CanShowInViewportPanel` (`main.cpp:5093`) is a blocklist defaulting to
`true`.** Every new node type must remember to opt out or it silently gets
"Open in viewport panel" / "Open in new window" menu items that show a blank
box. Audio nodes were already excluded generically in a small fix immediately
preceding this phase (`main.cpp:5106-5112`, gated on
`dynamic_cast<IAudioSource*>` or `AudioInputSlot(0) != nullptr`) — **that fix
is already in the tree; do not redo it.** Note its comment: P3d's Scope node
is the deliberate future exception, since its spectrum mode does emit a real
image texture.

**The right-click menu is shared with inline type gates.** `main.cpp:14654-14711`:
Hide/Show params, a Show/Hide viewport toggle gated on
`dynamic_cast<IGeometrySource*>` (`:14664`), Open in viewport panel, Open in
new window, Help. There is no per-node-family policy concept.

**Per-node UI flags already persist.** `GraphNode` (`src/core/GraphNode.h:36,42`)
carries `showParams` (defaults false) and `showMiniViewport`. They round-trip
through the patch file's `flags` line — written at `src/core/Patch.cpp:197-198`,
read at `:294-301` as exactly three whitespace-delimited ints.

## Design decisions — already made by the user, implement these, do not re-litigate

1. **Compact grid + expandable.** An audio node shows a small set of the most
   important params in a **multi-column compact grid**, plus one visualizer.
   An expand affordance reveals the full param set. Collapsed state keeps
   large patches readable; expanded state is where the user actually dials in
   a sound.
2. **Exactly one inline visualizer per node, relevant to that node.** Not a
   generic image preview. Oscillator → waveform trace. A filter → frequency
   response curve. An envelope → its ADSR shape. A meter/scope → its level or
   spectrum. Pick one per node type; do not stack three.
3. **No image viewport for audio nodes. No "Open in new window". No "Open in
   viewport panel".** Already enforced by the `CanShowInViewportPanel` gate
   described above. Do not add an audio-node projector-window path.
4. **Musically dense.** Every param a serious user would expect should exist
   on the node, reachable via expansion. Sparse is the failure mode being
   corrected here. See the researched inventory below.

## Researched param inventory for the reference Oscillator

Compiled from current commercial/open synth references (Bitwig Polymer,
Kilohearts Phase Plant, Ableton, Omnisphere, HALion FM, SynthEdit HD
Oscillator) — see Sources at the bottom. This is the target for "musically
dense"; it is a *menu to choose from with justification*, not a mandate to
ship all 20 controls.

**Tier 1 — collapsed view (the compact grid, ~4-6 controls):**
- `waveform` — sine / triangle / saw / square / pulse / white / pink / brown
  (the plan's §3 Oscillator already specifies noise types live here, not in a
  separate Noise node)
- `frequency` (Hz) or pitch, depending on whether a note cable is connected
- `volume` / level
- `pulseWidth` (meaningful only for pulse/square — grey it out otherwise)
- `unison` voice count
- `detune` (cents)

**Tier 2 — revealed on expand:**
- `octave`, `semi`, `fine` — coarse/fine tuning, standard on every synth
- `phase` — initial phase, and `phaseRandomize` / spread across unison voices
- `stereoWidth` — unison voice stereo spread
- `sync` — hard sync (off / internal ratio); pairs naturally with pulse waves
- **2-op FM section**: `fmRatio` + `fmIndex`. The plan's §3 explicitly scopes
  Oscillator to 2-op FM and explicitly rules 4-6-op DX-style FM out of scope
  — do not build an operator matrix here.
- `fmFeedback` — phase-modulation feedback, cheap and sonically valuable
- `glide` / portamento time
- `velToVolume`, `velToFilter` — velocity mapping (only meaningful once P3a's
  note cable carries velocity; wire the params now, note in your summary that
  nothing drives them until P3a)

**Deliberately NOT on this node (justify if you disagree):**
- Per-oscillator filter (`fmax`/`fmin`/`q`): the plan consolidates all
  filtering into the separate **Audio Filter** node (§3 Effects). Duplicating
  a filter inside Oscillator contradicts the consolidation this whole plan is
  built on. **This is the single most likely place to disagree with a
  reference implementation that does bundle one — if you build it, say why.**
- Per-oscillator amp envelope: same argument, that's the **Envelope**
  modulator (§3, P3a).
- Wavetable / drawable waveforms: the plan keeps **Wavetable** a separate node
  for exactly this reason (different UI, morphing, table previews).

## What to build

### 1. The design document (write this first, before any code)

`docs/plans/audio/audio-node-ui-system.md`. It is the artifact P3a-e sessions
will follow, so it must be prescriptive, not exploratory. Cover:
- The node body **layout grammar**: exact regions in order (title, visualizer,
  compact param grid, expand affordance, expanded param region, output pin),
  with concrete pixel sizes chosen against the existing `kPreviewSize` /
  `kParamWidth` constants so audio nodes sit visually consistent beside
  visual nodes.
- The **widget set** and when to use each (compact grid slider, compact
  dropdown, toggle, the visualizer). Include the rule that every audio param a
  modulator could drive must still expose a modulator input pin the way
  `ModSlider` does today — losing modulation to save space would be a
  regression, and audio params being modulatable by visual modulators is a
  core selling point of this app (see `docs/plans/audio/cook-rate-decision.md`).
- The **visualizer catalogue**: which visualizer each of the plan's 30 node
  types gets. One line each. This is the table P3 sessions look up.
- **Right-click menu policy for audio nodes**: which items appear, which are
  suppressed, and any audio-specific additions.
- **The cable-type compatibility matrix, as user-facing documentation** — see
  the dedicated section below.
- **Param density policy**: what belongs in the collapsed grid vs. behind
  expansion, as a rule a future session can apply to a node you never saw.
- **How density scales down**: a Gain node has one param. State what a
  one-param audio node looks like under this grammar so it doesn't end up with
  an absurd amount of chrome around a single slider.

### 1b. Cable compatibility must become visible — verified real problem

The user could not work out how to connect Oscillator → Gain. **The connection
rule is not broken** — `IsInputSlotCompatible` (`main.cpp:1623-1628`) correctly
accepts an `IAudioSource` into any pin whose `AudioInputSlot(slot)` is
non-null, and `AUDIOGRAPHTEST` wires that exact chain successfully on every
run. The failure is purely that the pin is invisible as an affordance:

- `INode::InputLabel(int)` defaults to `nullptr` (`src/core/INode.h:113`), and
  **neither `GainNode` nor `AudioOutputNode` overrides it**
  (`src/nodes/AudioNodes.h`). Their audio input therefore draws as an
  unlabelled bare dot in the node's top-left corner. Compare `OutputNode`,
  which labels its pins `"in"` / `"audio"` (`src/nodes/OutputNode.h`).
- Link *tinting* by cable type already exists (audio = blue `ImColor(90,150,255)`,
  note = green `ImColor(90,220,130)`, `main.cpp:13991-13999`) — but only once a
  link is already made. Nothing signals compatibility *before* or *during* a
  drag.

Fix as part of the design system, and document the rules:

**The matrix as currently implemented** (`main.cpp:1591-1700`) — verify this
still holds before writing it into the doc, then include it:

| Source | Image pin | Geometry pin | Modulator pin | Audio pin | Note pin |
|---|---|---|---|---|---|
| Image node | yes | no | no | no | no |
| `IGeometrySource` | no | yes | no | no | no |
| `IModulator` | no | no | yes | **no** | no |
| `IAudioSource` | no | no | no | **yes** | no |
| Note source | no | no | no | no | **yes** |

Plus single-type specialised pins: Camera, Light, Environment (HDRI only),
Palette (`IPaletteSource`), and the Material/Displacement texture slots.

Two entries above are deliberate but currently unexplained to the user, and
the doc must say so in user-facing language:
- Audio and Note are **strictly closed** — no coercion either way.
- **A visual modulator cannot cable into an audio param.** This is by design
  (`docs/plans/audio/cook-rate-decision.md`: the intended path is a published
  atomic read, not a cable) but the mechanism does not exist yet, so the drag
  silently refuses with no explanation. **Decide and state** whether P2.7
  should show a "why" (a refusal tooltip / status-bar reason) or leave it
  until the mechanism lands in P3 — recommendation: show the reason now, since
  a silent refusal is exactly what cost the user time here.

Required outcome: every audio and note pin carries a label, and the reason a
refused drag was refused is discoverable. Whether that is pin labels alone,
compatible-pin highlighting during a drag, a legend, or a tooltip is your
design call — but a bare unlabelled dot is not acceptable.

### 2. The widget/infrastructure work

- A compact multi-column param grid layout helper, alongside the existing
  `ModSlider`/`DropdownButton` rather than replacing them (visual nodes keep
  using the current full-width widgets — **do not restyle the existing visual
  node library in this phase**).
- An inline visualizer widget for audio nodes, and the waveform-trace
  implementation the Oscillator needs. **RT-safety matters here**: the
  visualizer must read from the existing `MeterRing` (`src/audio/MeterRing.h`,
  the audio→main SPSC path) or a main-thread-recomputed preview curve. It
  must never call into an `AudioNode` from the UI thread, and the audio thread
  must never touch ImGui. Also honour the plan's §1 drawing rules
  (`README.md`): decimated rings, ~30 Hz redraw, not per-frame full redraw.
- A per-node expanded/collapsed flag. `GraphNode` already has `showParams`
  (`GraphNode.h:36`); add a distinct `showAdvancedParams` rather than
  overloading it, since "params visible at all" and "showing the full set" are
  now two different things. **Persistence caveat, verified:** the patch
  `flags` line reads exactly three ints via `>>` (`Patch.cpp:296-297`). A
  fourth int appended is backward-compatible for *reading old patches* (the
  stream just leaves the 4th variable at its initialized value — make sure you
  initialize it), but confirm `ROUNDTRIPTEST`/`PATCHTEST` still pass, and
  check whether an older build reading a newer patch matters to you.

### 3. The reference node — the real Oscillator

Replace P2's proof-of-plumbing `OscillatorNode`
(`src/nodes/AudioNodes.h:20-40`, `src/nodes/AudioNodes.cpp:15-81`) with the
full node, built entirely through the new UI system. Keep the existing
two-object structure exactly as it is — it is correct and RT-safe: the `INode`
half pushes params in `CookIfNeeded`, the `AudioOscillatorNode` half does DSP
in `ProcessBlock`, communicating only through `ParamMailbox`.

DSP notes:
- `DspMath::PolyBlepOsc` (`src/audio/DspMath.h`) already provides band-limited
  `Sine`/`Saw`/`Square`. Pulse-width, triangle, and the noise types are new —
  implement them there, from primary literature, keeping the existing
  BLEP-correction approach for anything with a discontinuity.
- **`ParamMailbox` has a hard limit of `kMaxParams = 64`**
  (`src/audio/ParamMailbox.h`) and the current node uses index constants
  defined per-file (`kFreqParam = 0` etc., `AudioNodes.cpp:9-12`). A dense
  Oscillator will use many more indices. Verify you stay under 64 per node
  instance, and if the flat-index scheme gets unwieldy, say so rather than
  quietly exceeding it.
- Unison means N detuned oscillator instances per voice — that is a real CPU
  multiplier. Keep the count fixed-size/preallocated (no allocation in
  `ProcessBlock`), the same way `VoiceAllocator`
  (`src/audio/AudioVoice.h`) already sizes its voice vector once at
  construction.

Update `VisitParams` for every new param so save/load round-trips (the
existing pattern, `AudioNodes.cpp:71-75`), and update the node's `Help` text
if the help registry (`main.cpp:5585`) has an entry keyed by type name.

## Clean-room constraint — unchanged and still binding

## Build & verify

```bash
cmake --build build -j"$(sysctl -n hw.ncpu)"
```

```bash
.claude/skills/run-infinite-hygiene/driver.sh
```

Baseline is **39/40 passing**. The only expected failure is `PHASEATEST`
(a pre-existing, unrelated `"Smooth"` node-name collision the user has
already fixed elsewhere — **do not attempt to fix it, and do not report it as
a regression**). Pay particular attention to `ROUNDTRIPTEST` and `PATCHTEST`
if you add the fourth `flags` int, and to `AUDIOGRAPHTEST` (audio
delete-crash) since you are changing an audio node's lifetime surface.

```bash
INFINITE_DSPTEST=1 ./build/Infinite.app/Contents/MacOS/Infinite
```
Must still end `DSPTEST OK` (7 checks). If you extend `PolyBlepOsc`, add
coverage there for the new waveforms — a zero-crossing/frequency check and a
peak-amplitude check, matching the existing fixture's style.

Finally, launch the app and confirm by eye: spawn an Oscillator, check the
collapsed grid reads clearly, the visualizer animates, expansion reveals the
full set, and **verify the right-click menu offers no viewport/new-window
items**. Wire Oscillator → Gain → Audio Out and confirm it still makes sound.
