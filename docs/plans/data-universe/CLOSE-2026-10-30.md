## 1. The standard: what "done" means here

Every change had to pass all four gates before it shipped.

| Gate | Test | Bar |
|---|---|---|
| Keep only if better | A/B on the same takes, old build vs new | Better on the part's own measure, never worse elsewhere |
| Pads frozen | `paddump.js`: pcm of 102 pad takes vs reference | 102 / 102 identical |
| Nothing breaks | Every take of each touched part renders | 0 failed, 0 clipped, 0 silent |
| App healthy | Release build, `headless_smoke.sh`, `deploy_desktop.sh` | 0 fails; no debug UI in release |

The measures:
- **Sound:** `part_vs_library.py` compares each part with real sample-pack loops of the same part (centroid, low share, crest, and so on).
- **Notes:** `line_gate.py` compares generated lines with 4,000 POP909 melody bars (not a source).

## 4. What was learned

| Learning | Why it matters next time |
|---|---|
| Measure before fixing: the synths darkness was one octave setting, found only by dumping every sequencer's register | Dump the patch and look before tuning voices |
| A guardrail fitted on old renders can block a real improvement (octave 3: 4 of 34 takes failed the spectral gate) | Refit `spectral_gates.py` after big sound changes, or the gate freezes the old sound |
| More data is not always better: the Diva rows made leads and synths darker, so they stay out | Keep only if better, per source, not per bank |
| 32 bands can't tell a saw from a square once the filter closes (98% fitted as saw) | Analytic fits need a closed loop: render in Infinite, compare with the source render |
| Dataset files lie: Scaler's performance JSON and MIDI decode to garbage ticks; Kontakt "Chords" are single chords, not progressions | Check a source's shape before building on it |
| Separate random streams per decision (`notes:<part>:<style>:<seed>`) let one part change without moving any other draw | That's what kept pads byte-identical through every change |
| Degrees, not notes: storing everything as scale degrees per family makes one bar playable in every key | It also ships patterns, never a file's notes |
| Independent reference: gate against data that is not a source (POP909), or the test grades its own homework | Same rule for any future note or sound gate |

## 5. Local data: what we collect today and what is missing

Everything stays on the machine (`~/Library/Application Support/Infinite/`). Nothing is uploaded.

| Data | Today | Where | Feeds |
|---|---|---|---|
| Knob moves (hand, modulator, expression, gesture, prediction), bindings, transport, undo/redo, patch load | **Yes**, 814 sessions, 70 MB | `movement-log/*.mlog.z`, `stats.bin` | `UserStyle` knob resting places, usual tempo |
| Played notes: pitch, step, onset, velocity, length, chord size | **As summaries only** | `prediction/*_style.bin`, `*_profile.bin` | `UserStyle` note lean in Generate Samples |
| Raw MIDI performance (notes with time, key, bpm, which node) | **No** | | |
| Generated takes and what happened to them (kept, rerolled, dragged out, deleted) | **No** (only kept WAVs in `Recordings/`) | | |
| Audio features of kept / exported audio | **No** | | |
| Patch snapshots at save / export | Autosave only | `Infinite.autosave.inf` | |

The gap: we know how the player turns knobs, but not which *results* they keep. Without outcomes, nothing can
learn "better" for this player; it can only learn "usual".

### 5.1 Structure (decided)

One folder, one format per kind, one shared session id so every record can be joined.

```
~/Library/Application Support/Infinite/learning/
  sessions.jsonl          session id, start/end, app version, opt-in state
  movement/               (existing movement-log, moved under here, same .mlog.z format)
  midi/YYYYMMDD.mlog.z    note on/off, velocity, time in beats, key, scale, bpm, source node id
  takes/YYYYMMDD.jsonl    every Generate Samples take: style, part, seed, dots, key, bpm, attempt, outcome
  audio/YYYYMMDD.jsonl    features of kept / exported audio (the same 32 bands + centroid, crest, onsets
                          that part_vs_library.py measures); never the audio itself
  patches/                patch text at save and export, deduplicated by hash
  profile/                derived only: user_profile.json + the existing prediction .bin files
```

Decisions:
- **MIDI** reuses the movement log's writer (`MovementLog`: compressed, backpressure, retention cap) as a new record type, so there's no second logging system.
- **Takes** are the most valuable new data. Outcomes are: `kept` (dragged to a track or exported), `rerolled`, `edited` (a knob moved within 30 s), `deleted`, or `ignored`. That's the label every model is missing.
- **Audio** stores features, not WAVs. The WAVs the player keeps are already in `Recordings/`. Features are small and are what the models read.
- **Retention:** one shared cap (default 500 MB). The oldest raw logs go first; `profile/` is never dropped.
- **Off switch:** one "Learn from my playing" setting stops all writers and leaves existing files. A "Forget me" button deletes `learning/`.

### 5.2 User profile (decided)

`profile/user_profile.json` is rebuilt nightly from the raw logs. It's the one file the generator and Prediction
nodes read.

| Block | Built from | Used by |
|---|---|---|
| Harmony: key and scale shares, chord sizes, progressions played | `midi/` | note bank draw weights (lean toward degrees this player uses) |
| Melody: step and leap shares, range, density, onset grid, swing | `midi/` | lead / motif / bass line choice from the bank |
| Sound: kept-take audio features per part (centroid, low share, crest) | `audio/` + `takes/` | per-part brightness and weight targets |
| Taste: keep rate per style, part, voice source (Vital / designed / bank line) | `takes/` | style and voice probabilities (the 50 / 60% shares become per-player) |
| Hands: knob resting places and ranges per role | `movement/` (existing) | `UserStyle` (unchanged) |
| Tempo | `movement/` transport (existing) | `UserStyle` (unchanged) |
| Trust: evidence count per block, n / (n + n0) | all | how far each block may pull from the style cards |

```
 raw logs ──nightly──> user_profile.json ──> Generate Samples draws (bank weights, voice shares)
    ^                                    └──> Prediction nodes (existing .bin profiles)
    └──── takes: kept / rerolled / edited ◄── player
```

The style cards stay the baseline underneath. A new player gets the cards; a player with thousands of kept takes
gets mostly their own taste. That's the same trust rule `UserStyle` already uses.

### 5.3 How the models improve from it

| Model | Signal | Gate before it changes what ships |
|---|---|---|
| Note bank weights | kept vs rerolled takes per bank line and progression | keep rate up on held-out sessions |
| Voice shares (Vital / designed) | kept vs rerolled per voice source and part | keep rate up; pads still identical |
| Spectral gates | kept-take audio features | refit; false rejects on kept takes ≤ 3% |
| Role critic | kept takes labelled by part | FRR ≤ 3%, catch ≥ 96% (its existing bars) |
