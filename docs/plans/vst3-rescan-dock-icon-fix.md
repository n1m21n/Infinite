## UPDATE (tested, still broken)

Built with `INFINITE_ENABLE_VST3=ON` and ran on the user's desktop: the
`SuppressAppUIForScanChild()` fix (commit `ea78a72`) does **not** stop the
Dock-icon flood. Rescan was clicked with real VST3 plugins present and the
Dock still filled with spurious "Infinite" icons. So the root-cause theory
in this doc (an AppKit-created default-policy shared app during a scanned
plugin's Cocoa static init) is either wrong, incomplete, or the fix isn't
actually taking effect before the plugin code runs. Do not assume this part
is done — start step 3 below from scratch, and treat step 3's "if icons
still appear" branch as the actual starting point, not a fallback. Also
worth checking things not previously considered: whether `posix_spawn`
itself (not just AppKit) causes the re-exec'd process to inherit Dock
visibility from `LSUIElement`/`Info.plist` activation settings in a way
`setActivationPolicy` can't override after the fact, whether the child
needs `NSApplicationActivationPolicyProhibited` set *before* `posix_spawn`
even returns (i.e. via an environment variable or argv flag the child reads
before any AppKit symbol is touched, since Objective-C class `+load`/static
initializers inside the plugin's bundle can run before `main()`'s explicit
call to `SuppressAppUIForScanChild()` on line 23555), and whether Dock icons
are appearing for a completely different reason unrelated to AppKit (e.g.
LaunchServices registering each re-exec'd process by PID regardless of
activation policy).

blocklist should already be catching them — check

would be a real bug in the crash-isolation path, not just the Dock-icon
issue) has not been determined yet — check `procPath` and `pid` in each
report against the app's own PID at the time versus a spawned child's PID.
If it's the parent, this dispatch-queue crash is worth investigating before
the Dock-icon issue, since a parent-process crash defeats the entire point
of out-of-process scanning.

## Background

Clicking "Rescan plugins" in the Plugins panel was observed opening dozens
to hundreds of spurious "Infinite" instances in the macOS Dock within a few
seconds (user-reported, screenshot showed a long row of duplicate app icons
in the Dock).

Root cause, confirmed by reading the code:

- `PluginScanner::StartScan` → `ScanThreadMain` (`src/audio/PluginScanner.cpp:95-98`)
  calls `Platform::EnumerateVST3Plugins`.
- The real VST3 implementation of that function lives in
  `src/platform/PluginVST3.mm` (line ~1608). For crash-safety, it does not
  load each `.vst3` bundle in-process — instead
  `ProbeVST3BundleOutOfProcess` (`src/platform/PluginVST3.mm:404`)
  `posix_spawn`s a **re-exec of the app's own binary itself**
  (`Platform::ExecutablePath()`), once per bundle found on disk, passing
  `--vst3-scan-bundle <bundlePath>` as argv. This means a folder with N VST3
  plugins spawns N short-lived child processes during one Rescan.
- The child mode is handled in `src/main.cpp:23549-23579`: when
  `argv[1] == "--vst3-scan-bundle"`, it calls `Platform::DescribeVST3Bundle`
  (which loads the plugin's real bundle code, `CFBundleLoadExecutable` etc.)
  and exits before `glfwInit()` — no window is created deliberately.
- The bug: some VST3 bundles have a Cocoa-based editor, and their factory /
  static-init code touches `[NSApplication sharedApplication]`. Because the
  child is a re-exec of the same signed app binary (same bundle identity),
  AppKit lazily creates a **default-policy** shared application for that
  process the first time anything touches it — which is exactly what makes
  a process show up as its own Dock icon/window. With dozens of bundles
  scanned in quick succession, dozens of Dock icons flash up.

## What's already been done (uncommitted work found and committed this session)

Commit `ea78a72` on `osc-feature` (merged at `779307a`, already pushed to
`private/main`) adds `Platform::SuppressAppUIForScanChild()`
(`src/platform/Platform.mm`, right after `ClearVST3Blocklist`/near
`ExecutablePath`) and calls it as the very first thing inside the
`--vst3-scan-bundle` branch in `main.cpp:23555`, **before**
`DescribeVST3Bundle` runs any plugin code:

```cpp
void SuppressAppUIForScanChild()
{
   @autoreleasepool
   {
      [NSApplication sharedApplication];
      [NSApp setActivationPolicy:NSApplicationActivationPolicyProhibited];
   }
}
```

The idea: claim the `NSApplication` singleton ourselves first, with
`NSApplicationActivationPolicyProhibited` (no Dock icon, no menu bar), so
that whatever the plugin does afterward finds the singleton already created
and already invisible — nothing it does can make the child visible.

The same commit also switched AU plugin instantiation
(`PluginCreate` in `src/platform/Platform.mm`) from the async
`instantiateWithComponentDescription:options:completionHandler:` API to the
synchronous `[[AUAudioUnit alloc] initWithComponentDescription:options:error:]`
initializer, to fix a `dispatch_assert_queue` crash seen with some Qt-based
AU plugins (Native Instruments Massive X / Pigments) whose init code
apparently needs to run on the calling (main) thread and can't rely on the
async completion handler's "arbitrary queue" guarantee.

**Neither change has been built or tested on this machine.** This prompt's
job is to verify both, not to assume they're correct just because they read
correctly.

## What is NOT touched by this fix (verify it still works)

The crash/hang-safety mechanism is independent of the Dock-icon fix and
should be unaffected, but confirm it: `ProbeVST3BundleOutOfProcess`
(`src/platform/PluginVST3.mm:404` onward) spawns the child, waits with a
timeout, and on hang/crash/nonzero-exit reports `ProbeOutcome::Crashed`,
which `EnumerateVST3Plugins` uses to add the bundle to the persisted
blocklist (`Platform::VST3Blocklist()` / the sentinel-file mechanism
described in `src/platform/Platform.h` above `VST3Blocklist()`). The Plugins
panel surfaces this list in `src/main.cpp` around line 9049
(`gPluginScanner.FailedBundles()`) and the blocklist UI mentioned around

was also tweaked in commit `ea78a72` from "crashed a previous scan" to
"crashed or hung while scanning", confirm that's still accurate wording for
what's actually surfaced).

## Steps

1. **Configure and build with VST3 enabled** — it's `OFF` by default
   (`CMakeLists.txt:38`):
   ```
   cmake -B build -DINFINITE_ENABLE_VST3=ON
   cmake --build build -j"$(sysctl -n hw.ncpu)"
   ```
   Confirm it compiles clean. `external/vst3sdk` is a vendored submodule —
   if the build fails with the SDK not found, run
   `git submodule update --init --recursive` first.

2. **Get VST3 plugins to scan.** If there are no VST3 plugins installed on
   this machine yet under the OS-standard directories
   (`/Library/Audio/Plug-Ins/VST3`, `~/Library/Audio/Plug-Ins/VST3`), check
   whether any are already installed; if not, ask the user which VST3
   plugins they'd like used for this test rather than installing anything
   yourself. Ideally include at least one plugin known to have a Cocoa
   editor GUI, since that's the class of plugin that triggered the bug.

3. **Run the app, open the Plugins panel, click "Rescan plugins".** While
   the scan runs (watch `gPluginScanner.IsScanning()` / the "scanning... (N
   found)" label at `src/main.cpp:9001`), watch the Dock. Confirm:
   - No extra "Infinite" Dock icons appear during the scan.
   - No extra windows steal focus or flash on screen.
   - The scan still completes and populates the plugin index (check the
     Plugins panel list, and/or `~/Library/Application Support/Infinite/PluginIndex.json`).

   If icons still appear, the likely next thing to check is whether
   `SuppressAppUIForScanChild()` is actually being reached before the
   plugin's own init code runs — add a temporary log line, or check whether
   `DescribeVST3Bundle` does anything (e.g. loads a nib, runs a Cocoa
   factory) *before* `main.cpp` calls `SuppressAppUIForScanChild()` — it
   currently doesn't, but re-verify against whatever `DescribeVST3Bundle`
   does now in case it changed.

   Also check `~/Library/Logs/DiagnosticReports/` for fresh `Infinite-*.ips`
   crash reports generated during this run, the same way the two saved in
   `docs/crash-reports/` were found — compare against those to see if the
   same dispatch-queue null-deref crash recurs.

4. **Verify crash/blocklist recovery still works.** If a plugin known to
   crash on scan is available, confirm it gets killed, added to the
   blocklist, and the scan continues to completion rather than stalling. If
   no such plugin is available, you can simulate it: temporarily point
   `Platform::ExecutablePath()` or the scan at a bogus bundle path, or ask
   the user if they have a known-bad plugin to test with. Don't skip this
   check — the Dock-icon fix runs in the same child-process code path this
   mechanism depends on, so a subtle ordering mistake could break both at
   once.

5. **Verify AU scanning/instantiation still works** after the sync-init
   change in `PluginCreate`. Load an Audio Unit plugin (not VST3) through
   the normal node-graph path (drag a Plugin node, pick an AU plugin) and
   confirm it loads, its editor opens, and audio passes through it
   correctly. If Native Instruments Massive X or Pigments (or another
   Qt-based AU plugin) happens to be installed, specifically confirm it no
   longer crashes with the `dispatch_assert_queue` trap the commit message
   describes.

6. **Fix anything still broken**, then re-run
   `.claude/skills/run-infinite-hygiene` (or at minimum the audio param/
   teardown sweeps it wraps) before considering this done, since this
   touches plugin load/teardown paths.
