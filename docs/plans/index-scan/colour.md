## What Infinite does today
- Oklab is used in exactly one place: `src/nodes/PaletteNode.cpp:40-62` (`LinearToOklab`, `OklabToLinear`). The sRGB transfer is exact (piecewise) at `PaletteNode.cpp:31,37`. k-means runs in Oklab (`PaletteNode.cpp:269-285`). Hue shift is a rotation of the a/b plane and saturation is a scale (`PaletteNode.cpp:454-460`). Lightness is clamped to [0,1] (`:460`). `LabToDisplay` (`:65-71`) runs `OklabToLinear` then `LinearToSrgb`, which clamps per channel (`:35`). That is a hard clip, with no gamut mapping, so boosting `saturation` shifts hue and lightness on out-of-gamut swatches.
- The Palette strip interpolates swatches in display-sRGB space: `PaletteNode.cpp:~500` (`rgb[c] = mSwatch[i][c] + ... * frac` inside `RebuildStrip`).
- Color Ramp (`src/nodes/ColorRampNode.cpp`): stops are lerped in raw stored RGB (`ColorRampNode.cpp:~125`, `Evaluate`), baked into a 256-entry `GL_RGB8` LUT (`RebuildLut`, `:138-160`). Luminance is looked up with Rec.601 weights (`:21`). Interpolation modes are "Linear" and "Constant" only (`:11`). `AudioColorRampNode` has its own mode list (`AudioColorRampNode.cpp:13`); I did not read its interpolation.
- Colour grade FilterDef (`src/core/FilterDefs.cpp:~985-1042`): everything is done in display-referred sRGB values. Hue shift and saturation use `rgb2hsv`/`hsv2rgb` (`:47`, `:1004-1008`), and vibrance is a lerp to the channel average (`:1010`). The Tone Shaper is a per-channel curve. Exposure, tonemap and HDR are absent from this filter.
- Predictive Coloring (`src/nodes/PredictiveColoringNode.cpp:50-104`) is the most careful grade: it decodes with `pow(c, 2.2)` (`:63`), applies gain, exposure, levels and tone zones in linear, does HSV sat/vibrance/hue, then `pow(1/2.2)` (`:104`). So the codebase has three sRGB conventions: exact piecewise in Palette, gamma 2.2 in Predictive Coloring and in Render 3D (`Geometry3DNodes.cpp:232-233`, `toLinear`/`toSrgb`), and no transform at all in FilterDefs/ColorRamp/Blend. Not a bug in isolation, but a mixing hazard.
- Blend (`src/nodes/BlendNode.cpp:19-28`, `src/core/BlendModes.h`): a ~30-mode switch operating directly on stored texture values (no linearisation, no spectral option). Textures are plain `GL_RGBA8` (the sRGB convention noted in codebase-navigation).
- Tone mapping exists only in Render 3D: `Geometry3DNodes.cpp:30` (`"None","ACES","Reinhard"`), `acesFilm` is the Narkowicz fit at `:234-236` and `:475`, applied at `:279-280` and `:781-782`, then `toSrgb` (gamma 2.2). No 2D tone-map filter exists (grep of src/ for `ACES|Reinhard|tonemap|filmic|AgX|Hable` found only Render 3D, the tests, and the Startup/Bench setup). `GLUtil` supports `GL_RGBA16F`/`32F` FBOs (`GLUtil.cpp:124`, `GLUtil.h:26`), so an HDR 2D chain is feasible.
- Field has `mix`/`lerp` and `smoothstep` as builtins (`FieldVM.cpp:54,80`, `ElementBackend.cpp:987`), but no colour-space builtins. A grep of `src/core/field/*.cpp` for hsv/oklab/srgb found no colour builtins. Presets inline their own hsv code (`FieldPixelNode.cpp:277,770`). The Field "Color Gradient" preset is a plain RGB `mix` between two hardcoded colours (`FieldPixelNode.cpp:215`).
- Searches that returned nothing relevant: `kubelka|reflectance|gamut` in src/ (only unrelated "aces" substrings in "places"). No Kubelka-Munk, no gamut mapping, no OKLCH interpolation, and no `GL_SRGB8_ALPHA8`.

## What the peers do differently
- Spectral.js `mix` (`spectral.js`, ~line 363): it up-samples each sRGB colour to a 38-sample reflectance curve (380-750 nm, 10 nm) as a weighted sum of 7 basis spectra W/C/M/Y/R/G/B (`lRGB_to_R`, `BASE_SPECTRA`). It converts each to K/S = (1-R)^2/(2R), averages K/S per wavelength with weights c = f^2 * tintingStrength^2 * luminance, inverts with R = 1 + KS - sqrt(KS^2 + 2KS), and integrates against CMFs/D65 to XYZ then linear RGB. Blue + yellow gives green, as paint does. Cost: 38 bins x N colours per mix. `gradient` and `palette` are just this mix with weights (1-t, t).
- Spectral.js `gamutMap` (CSS-style): converts to OKLCh, binary-searches chroma at fixed L and h, accepting the first chroma where clip error in OKLab deltaE is < jnd (0.03). It returns white if L>=1 and black if L<=0.
- Color.js `toGamutRayTrace`: a newer CSS Color 4 algorithm. It casts a ray from the achromatic anchor (same L, chroma 0) toward the colour and intersects the RGB cube with the slab method (`raytrace_box`). It does 4 iterations, resetting L and h to the originals each time. No search loop, so it is cheap and GPU-friendly. `toGamutCSS` is the binary-search sibling (same as Spectral.js).
- Color.js `interpolation.js`: interpolation in a chosen space, with hue arc fix-up ("shorter", "longer", "increasing", "decreasing") and premultiplied-alpha handling where the hue angle is never premultiplied.

## Concrete improvements

### Existing nodes first
1. **Palette: gamut-map instead of per-channel clip** (S). Replace the clamp in `LabToDisplay` (`PaletteNode.cpp:65-71`) with a fixed-L/h chroma reduction (Spectral.js `gamutMap` / Color.js `toGamutCSS`) or the 4-iteration ray trace. Benefit: the `saturation` and `brightness` sliders (`:454-460`) stop skewing hue and lightness on swatches that leave sRGB, and neon/saturated photos keep their look. The Palette node's tests would need a new case. Skill: none (a localised edit). Licence: MIT, both. The idea is a CSS Color 4 algorithm, so reimplement from the algorithm, with no attribution beyond a comment.
2. **Color Ramp: interpolate in Oklab (or OKLCh with hue arc) and bake the LUT in a correct space** (S-M). The current linear stop lerp (`ColorRampNode.cpp:~125`) in stored RGB produces muddy midpoints (blue to yellow goes grey). Add interp modes beside "Linear"/"Constant" (`:11`): "Oklab", "OKLCh shorter hue", and optionally "Spectral". Reuse the Oklab helpers moved out of `PaletteNode.cpp` into a shared `src/core/ColorSpace.h`. The LUT is CPU-built (`RebuildLut`), so even Kubelka-Munk is free at 256 entries. The mode is saved via `VisitParams`, so a new int param must default to the old behaviour for old patches. Skill: `new-compositing-node` / `node-param-audit` for the param. Licence: MIT for Color.js; the Oklab formula is already in-tree.
3. **Palette strip smooth mode in Oklab** (S): `PaletteNode.cpp:~500` blends display sRGB; do it in the existing Oklab centres, or spectrally. Same helper as item 2.
4. **Blend: add a "Spectral (Kubelka-Munk)" mix mode** (M-L). The blend shader is a single `uMode` switch (`BlendNode.cpp:19-28`; mode list in `BlendModes.h`). The GPU cost is the issue: 38 bins per pixel. Cheaper option: precompute the K/S for the 7 basis spectra into a small texture/uniform array and evaluate the weighted-sum up-sample + mix in 38 iterations. A GPU port has not been read (404), so the cost is unverified. Benefit: paint-like feedback and trails when crossfading. Skill: `new-compositing-node` (BypassSource rule applies) and `compositing-pipeline-sweep`. Licence: MIT, so an algorithm reimplementation needs no attribution, but the basis spectra tables are data from Scott Allen Burns' LHTSS method as adapted by the author. If the tables are copied, keep the MIT notice and credit Burns/van Wijnen. Prefer deriving our own tables.
5. **Unify the sRGB transfer** (S, a correctness item, not from the peers): three different conventions are in the tree (exact piecewise in Palette, 2.2 in Predictive Coloring and Render 3D, none in FilterDefs). A shared `ColorSpace.h` with `SrgbToLinear`/`LinearToSrgb` (and GLSL snippet constant) would stop drift. Check `render-pipeline-sweep` before touching the 3D shaders, since changing 2.2 to piecewise shifts every existing render slightly.
6. **Colour grade filter in linear/Oklab** (M): the FilterDefs grade (`FilterDefs.cpp:985-1042`) does HSV sat/hue in display space. Moving hue/saturation/vibrance to Oklab chroma/hue rotation (same math Palette already uses at `:454-460`) gives perceptually uniform results. Changing the FilterDef changes saved looks, so it would be a new mode/toggle. Skill: `new-effect-node`. Licence: none needed (Ottosson's formula is already in tree).
7. **Tone mapping for the 2D chain** (M): Render 3D has ACES/Reinhard (`Geometry3DNodes.cpp:30`). There is no 2D "Tone Map" filter with exposure and operator choice, even though RGBA16F FBOs exist. No tone-mapper source was read here (the Tony McMapface repo was unverifiable); suggest a FilterDef using public analytic operators (Narkowicz ACES is already in tree; Reinhard extended / Hable). Skill: `new-effect-node`. Effort S for a FilterDef, but only useful when upstream nodes emit HDR; check which nodes use `GL_RGBA16F` first.

### New nodes
8. **Field colour builtins** (M): add `oklab2rgb`, `rgb2oklab`, `hsv2rgb`, `srgb2lin` etc. to Field so presets stop inlining hsv (`FieldPixelNode.cpp:277,770`) and can build palettes (gradient preset at `:215`). Touches the lexer/IR/three backends (VM, GLSL, sample), so follow `field-compiler` and `field-integration`, and add corpus entries per `field-testing`. Licence: n/a (our own implementations).

## Nothing to learn
- Oklab conversion itself: Infinite already has the correct matrices (`PaletteNode.cpp:43-62`). Nothing from the peers' Oklab code is needed, only a move to a shared header.
- k-means palette generation: Palette does this in Oklab already, deterministically seeded (`PaletteNode.cpp:~85`). Neither peer does palette extraction, so there is no gap to close.
