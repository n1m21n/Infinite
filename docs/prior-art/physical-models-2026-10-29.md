# Prior art: physical models for piano, wind/brass and better strings (2026-10-29)

## Problem
Infinite's engines (including the String node) never land inside measured guitar/harp/violin/cello/piano families (HANDOFF "String vs acoustic families": String ratios 4.3 to 7.1, farthest of all engines; "reach1 String": 17.3% closer than nearest, MISS). What DSP is missing, and is there permissively licensed open code to adapt into an Infinite node?

Method note: licences below were read from the repo's own LICENSE / README / per-file header (fetched 2026-10-29), not from memory. Only permissive code was opened. Clean-room disclosure: while checking the Faust library licence I ran one `grep` over `physmodels.lib` (LGPL) whose output showed about a dozen lines of Faust code and comments (guitarBridge/violinBody lines, one comment about STK Brass 0.03 vs 0.012 lip coefficient). Nothing from them is used or quoted here; nothing further was read from that file. Treat Faust `physmodels.lib` as off limits for the implementer.

## What Infinite's String node has today (read from `src/nodes/StringNode.{h,cpp}`)
- One transverse waveguide loop per voice (max 8 voices): integer delay + 3-tap linear-phase loss filter (`b`, `tone`) + 4 identical first-order dispersion allpasses (`stiffness`) + tuning allpass. Per-voice T60 via loop gain.
- Exciters: pluck and strike are the same thing, a Hann pulse of `pulseLen` samples injected at the pick point (`position`) in both rails; bow is Smith's friction junction `r = (|3.5 dv| + 0.75)^-4` with a 40 ms on / 15 ms off envelope and oversampling `os` for short loops.
- Body: ONE fixed bank of 10 bandpass modes (98 Hz to 3300 Hz, constants in `kBodyModes`), dry/wet mix by `body`. Not a parameter set, not per-instrument, not coupled to the string.
- Absent: no hammer model (no felt nonlinearity, no velocity-dependent spectrum, no hammer mass/contact time), one string per note (no 2 to 3 unison strings, so no beating and no two-stage decay), single polarisation, no longitudinal/phantom partials, no sympathetic strings, no per-partial (frequency-dependent) decay beyond one loss filter, no bridge coupling, no finger/fret/pick filter, no commuted excitation, no body impulse response, no noise (bow hiss, key thump), no wind engines at all.

## Patterns across sources
- Every permissive source treats instruments as small waveguide + nonlinearity blocks with hand-set constants. None ships a fitted per-instrument parameter table. The "learned compact parameter set" is therefore Infinite's own contribution: the DSP skeleton is open, the numbers must be fitted from the instrument library.
- The one thing the permissive code does have that Infinite's String does not: multi-mode resonators with per-mode decay (Elements/Rings), a reed/lip nonlinearity coupled to a bore (Elements Tube, STK Clarinet/Brass), and per-string coupling at a bridge (STK Guitar, mathsound).
- Piano-specific machinery (hammer nonlinearity, 2 to 3 strings per note, beating and two-stage decay, longitudinal/phantom partials, soundboard filter) exists as open papers (Bank, Smith, Chabassier) and one fresh MIT/Apache prototype, but no mature permissive C++ implementation turned up.
- Mixed-licence traps: Soundpipe (MIT label, Csound-derived modules), eurorack (AVR code GPL, STM32F MIT, `third_party/STM` separate, trademark clause), Faust libraries (LGPL + generated-code exception).

## Mapping to Infinite: new DSP in String, or a new node

Facts are what the code shows; recommendations are inference.

| Family | Gap vs `StringNode` (fact) | Best algorithm | Best permissive implementation | Recommendation |
|---|---|---|---|---|
| Piano | No hammer (Hann pulse only), one string per note, no beating or two-stage decay, no longitudinal or phantom partials, no bridge or soundboard coupling | Waveguide strings with implicit nonlinear hammer + 2 to 3 coupled unison strings + dispersion + Bank-style two-stage decay + soundboard modal/FDN; commuted synthesis as the cheap fallback | Design reference: mathsound (MIT/Apache); skeleton: STK/Elements for string pieces; papers: Bank, Smith PASP | **New node** (`PianoNode`). | Plucked with body | Body is 10 fixed constants; plucked and struck both a Hann pulse; no pick/finger filter, no commuted body IR, no string-to-body feedback | Extended KS + pick-position comb + pick filter + body modes fitted per instrument (or commuted body IR); bridge coupling | STK `Guitar`/`Twang` (structure), Elements/Rings modal resonator (structure of a learned mode table) | **Extend String**: make `kBodyModes` a loadable table (freq, Q, gain per mode, per instrument), add pick filter and pick-shape options, optional 2-polarisation pair. | Bowed with body | Friction junction exists and matches the standard form; bow envelope fixed 40/15 ms; no bow-force/position as separate controls, no bow noise, no bridge to body feedback | MSW friction table + body filter fitted per instrument + bow noise | STK `Bowed` (bow table, Maestre contribution), Elements `BowTable` | **Extend String** (bow noise, bow pressure/position controls, body table). | Woodwind (clarinet, sax, flute) | Nothing equivalent in repo | Bore waveguide + reed table (clarinet/sax) or jet table (flute), one-pole reflection, bell/radiation filter, breath noise | Elements `Tube` (smallest), STK `Clarinet/Saxofony/Flute` | **New node** (`WindNode`) with an `excitation` selector: reed / jet / lip |

Learned parameter sets (inference): per instrument store only (a) body modes (freq, damping, gain, tens of numbers), (b) loop filter / decay vs pitch curve (a few numbers per octave), (c) inharmonicity B vs pitch, (d) excitation shape (pluck/hammer spectrum), and for wind (e) reed/lip stiffness, bore loss, bell cutoff. These all fit in a few hundred floats per instrument.

## Open questions
- Patent notice in STK headers ("Stanford University, Yamaha, and others"): does the owner want a legal read before shipping waveguide-based wind? (Inference: the generic waveguide and Karplus-Strong patents are old; no check done.)
- mathsound's reference data (Salamander Grand V3) has its own licence; any fit against it, and any use of the Salamander files in training, needs that licence confirmed. Infinite's own instrument library measurements are the intended source, so this may be moot.
- Does the owner accept a new `PianoNode` and `WindNode` (two new nodes through `new-audio-node`) or want everything under String with a family switch? Recommendation above is 2 new nodes + extend String.
- Is Braids' MCU confirmed STM32F (needed to rely on the README's MIT line)? Not needed if only Rings/Elements/Plaits are used.
- First test to make before building: render the existing `kBodyModes` replaced by a fitted table for one guitar from the library and re-run `string_families.py`; if guitar ratio drops well below 4, the body table is the cheapest win (unrun: inference).
