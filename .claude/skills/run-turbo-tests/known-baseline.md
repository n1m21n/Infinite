# Known baseline failures

Inherited from the macOS hygiene driver. These checks report FAIL by design or because the generic sweep rig cannot observe the param (no sample loaded, gated by a sibling default, effect longer than the probe window, ...). They are not regressions unless the list changes.

Windows note: PLUGINSCANTEST (Audio Units) was dropped. PLUGINDRAGTEST and MEDIADRAGTEST depend on having VST3 plugins / media in the library panel; an empty library can time out and FAIL.

- known baseline (not a regression unless it changes): PHASE1TEST is occasionally flaky on particle-system timing; rerun once before treating it as a regression. PHASEATEST currently fails on a pre-existing "Smooth" node- name collision unrelated to audio work — see the spawned task to fix it.

- known baseline: AUDIOPARAMSWEEPTEST currently reports [FAIL] on one Dynamics param (sidechainExternal — every audio input slot a candidate has gets the identical drive-tone buffer aliased in, main and sidechain alike, so switching which pin the detector reads from can never change the signature), two Delay params (sync, rateDiv — both gate the base delay time itself, the very knob that would need to differ to observe a change, so unlike feedback/tone/pan/ducking they can't be gated behind a short-path prerequisite), rateDiv alone (not sync — see below) on Chorus, Flanger, Phaser, Stutter and Tremolo (identical structural reason, same MusicTime table — Tremolo's own sync/rateDiv/rate comment in EffectDefs.cpp already says as much, it was just missing from this baseline list), and three Reverb params (decay, damping, predelay — all only change what the FDN's 8 lines *write*, and a line's own read trails its write by ~600-1100 samples at the default size, longer than the sweep's post-alteration measurement window). All hand-confirmed correct — see EffectDefs.cpp's comments on each param and .claude/skills/audio-node-sweep/SKILL.md's blind-spots section.

- known baseline: Chorus/Flanger/Phaser/Stutter/Tremolo's sync param used to be baselined alongside rateDiv here too, but is no longer — each kernel's synced-vs-free rateHz/period default now differs enough (e.g. ChorusKernel: 0.5Hz free vs 2Hz synced quarter-note) that toggling sync alone is observable within the sweep's window. rateDiv still fails: EffectDefs.cpp gives it no {sync, 1.0f} prerequisite, so for these five (sync defaults false) it's probed with the sync branch dead - the same gated-param blind spot as Audio Filter's gain. Delay itself still fails both sync and rateDiv per the paragraph above (no kernel-timing escape hatch there).

- known baseline: AUDIOPARAMSWEEPTEST also reports [FAIL] on all nine Sample Player params (pitch, finetune, speed, start, end, volume, loop, reverse, pingpong - registered type name is still "Sampler"). The sweep's generic rig constructs a bare throwaway instance with no file loaded, and an unloaded Sample Player is silent by design (matching Audio File's "no file loaded" behaviour) - with nothing playing, no param can ever produce a measurable difference in the rendered signature. Confirmed correct by loading a real sample and checking each param (plus reverse/pingpong/end behaviour and the record input) audibly/visibly changes playback; see SAMPLERTEST inside RunSamplerFixture in main.cpp, and SamplerNode.cpp's ProcessBlock.

- known baseline: AUDIOPARAMSWEEPTEST also reports [FAIL] on Note Router's probability (redistributes events across its multiple output ports, but the sweep's generic rig only ever reads port 0 via NoteOutbox()) and on Note Capturer's loop/quantizeDiv (both only take effect via an explicit record/play transport command the generic rig never issues, so the node never leaves its idle state during the probe). Confirmed correct by reading NoteNodes.cpp's AudioNoteRouterNode::NoteOutbox(int) and AudioNoteCapturerNode::ProcessBlock's mCommand switch.

- known baseline: AUDIOPARAMSWEEPTEST also reports [FAIL] on every Drum Sequencer param (all 8 lanes' laneN_volume/pan/pitch/finetune/decay/ transient/start/end/mute/solo/choke and laneN_step0..step7 - the real VisitParams names, not the doc-prose "steps" singular this paragraph used to say - plus global rate/steps/swing/volume/run and the four global offset knobs: globalTransient/globalDecay/globalPitch/ globalPan). Same root cause as Sampler above: the sweep's generic rig builds a bare throwaway instance with no lane sample loaded, and a lane with nothing loaded is silent by design (docs/plans/audio/drum-sequencer-v2-prompt.md §2) - with nothing playing, no param can produce a measurable difference in the rendered signature. Confirmed correct with real loaded samples in RunDrumSequencerFixture (DRUMSEQTEST) in main.cpp, which exercises every one of these params (timing, swing per-lane and global, velocity, choke, solo/mute, decay, start/end range, global offset composition, voice- steal, transport agreement, run toggle) against real audio and passes.

- known baseline: AUDIOPARAMSWEEPTEST also reports [FAIL] on Plugin's bypass and map_slots. This one is by design, not a rig limitation: a hosted plugin's parameters deliberately do NOT go through ParamMailbox - they are pushed straight to the plugin with Platform::PluginSetParameter, because the plugin owns its own parameter smoothing and one mailbox slot per mapped param would blow past ParamMailbox's 64-slot ceiling (see AudioPluginNode.h). bypass does reach the audio thread, through its own atomic rather than the mailbox the sweep watches, and map_slots is a serialization-only count of how many mapping rows to write - it has no audio meaning at all. The sweep also builds a bare instance with no plugin loaded, which renders pass-through by design, so nothing it can set could change the signature either way. Confirmed by INFINITE_PLUGINSCANTEST (real AU: instantiate, render, set and read a parameter, save/restore fullState) and INFINITE_PLUGINDRAGTEST.

- known baseline: AUDIOPARAMSWEEPTEST also reports [FAIL] on Limiter's release. Confirmed by direct simulation of the kernel's own math against the sweep's exact probe/block timing: the probe tone is two channels in phase quadrature (L=sin, R=cos), so the stereo-linked per-sample level ripples with a ~40-sample period, but this kernel's peak detector takes the max over its full ~72-sample lookahead window (wider than that ripple), which lands on a fixed value once warmed up - nothing left for release to chase. threshold has explicit testCandidates and passes; see EffectDefs.cpp's comment on Limiter's release param.

- known baseline: AUDIOPARAMSWEEPTEST also reports [FAIL] on all eight of Note Stack's semiN params (semi0..semi7 - enabledN itself passes for all eight). Same root cause as Note Router/Sampler above: each semitone only affects the voice it belongs to, and the sweep's generic rig builds a bare throwaway instance with every enabledN false by default, so no voice is sounding for any semiN to be observed on. Confirmed correct by RunNoteStackFixture (DSPTEST notestack ...) in main.cpp, which enables real voices and checks the exact transposed pitches, the dedupe rule, and the out-of-range drop - all against the live semitone values. Note Stack's sweep also now fails a 9th param, useGlobalScale - same root cause as semiN: the scale-snap call sits inside 'if (!ens[v]) continue' in NoteNodes.cpp, and every voice is disabled by default, so it's never reached either.

- known baseline: AUDIOPARAMSWEEPTEST also reports [FAIL] on Oscillator, Metallic, Wave Terrain and Wavetable's frequency (all four share one cause: each has a note-input pin, so the sweep's rig always wires a note cable and these nodes only read frequency in their free-running branch, gated on no-note-driven - see OscillatorNode.h's 'ignored when note-driven' comment, WavetableSynthCore.h and MetallicNode.cpp/WaveTerrainNode.cpp's isNoteDriven checks - so free-run mode is structurally untestable by a rig that always holds a note), and on glide for the same three synth-voice types (wired correctly into pitch smoothing, but every new voice snaps its glide state immediately to the trigger pitch - WavetableSynthCore.h's SetImmediate, MetallicResonator.h's pitchSmoother.SetImmediate - and the rig always retriggers the identical note, so there is never a pitch distance to glide across). Also fmMode (gated by fmDepth's 0.0 default), cutoff/resonance (gated by filterType's Off default), and detune/stereoWidth/phaseRandomize on Wavetable's a.* engine (gated by unison's 1 default - phaseRandomize spreads unison voices' start phase same as detune spreads their pitch, so it's a no-op with one voice too - same class WaveTerrain already declares via SweepPrerequisitesFor but Oscillator/Wavetable don't). None of these are dropped mailbox pushes - every one reaches its atomic/ParamMailbox/ SmoothedValue read site; confirm by hand: unplug the note pin and sweep frequency, or set unison=2/filterType!=Off/fmDepth>0 before touching the gated param, or trigger two different pitches in sequence for glide.

- known baseline: AUDIOPARAMSWEEPTEST also reports [FAIL] on Wavetable's a.warpMode/a.warpAmount/a.warpRatio (WarpSample in WavetableSynthCore.h returns the input sample unshaped whenever warpAmount is 0, which is a.warpAmount's own default - same gated-by-sibling-default class as fmMode/fmDepth above), a.filterAmount/filterAttack/filterDecay/ filterSustain (a.filterAmount also defaults to 0.0 - same exp2f(0)=1 reasoning as Wave Terrain's filterAttack/Decay/Sustain/Release below, on top of a.cutoff/a.resonance's own filterType=Off gate - filterRelease is additionally covered by the note-off paragraph below), a.pitchAttack/ pitchDecay/pitchSustain/pitchRelease (a.pitchAmount defaults to 0.0 semitones, so the pitch envelope's shape multiplies zero regardless of its own ADSR), and a.fine (read live into every voice's pitch every block with no gating - WavetableSynthCore.h line ~446 - but it is a pure frequency shift, and this synth's peak+RMS signature doesn't move enough for one to register within the sweep's epsilon; same class as Spectral Synth's fine below).

- known baseline: AUDIOPARAMSWEEPTEST also reports [FAIL] on Wave Terrain's ratioA/ratioB (only read by EvaluateOrbit's Lissajous case in WaveTerrainDsp.h - default orbitType is Circle, which ignores both), its filterAttack/Decay/Sustain/Release (WaveTerrainNode.cpp computes modulatedCutoff via exp2f(filterAmount * filtEnv), and filterAmount defaults to 0.0 so exp2f(0)=1 regardless of the envelope), and on ampRelease/filterRelease on Wave Terrain/Oscillator/Wavetable generally (the sweep's PushHeldNoteOn only ever pushes note-ons - there is no note-off anywhere in AudioParamSweep, so release-stage code is unreachable by this rig). Wavetable's a.ampSustain is the same window class from the other end of the envelope: a.ampAttack/ampDecay default to 4ms/300ms, so a held voice doesn't reach the sustain stage until ~304ms in, far longer than Check B's single ~10ms block - matching Reverb's decay/damping/predelay reasoning above (correct, just slower than the sweep's post-alteration window).

- known baseline: AUDIOPARAMSWEEPTEST also reports [FAIL] on all ~28 of Wavetable's b.* params (b.on/table/position/volume/pan/unison/detune/ stereoWidth/octave/semi/fine/phase/phaseRandomize/warpMode/warpAmount/ warpRatio/filterType/cutoff/resonance/ampAttack/Decay/Sustain/Release/ pitchAmount/Attack/Decay/Sustain/Release/filterAmount/Attack/Decay/Sustain/ Release). One root cause: WavetableNode.cpp defaults engines[1].on to false, and RenderEngine skips a disabled engine entirely (lastOut=0, continue) - same class as Note Stack's enabledN/semiN pattern above. Every b.* param is silent until b.on is flipped true first.

- known baseline: AUDIOPARAMSWEEPTEST also reports [FAIL] on all 20 Granular params and all 12 PaulStretch params. Same root cause as Sampler/Drum Sequencer above: AudioGranularNode::ProcessBlock computes hasSample from mSampleSlot.Active() and, if false, zeroes the output and returns before any param (including mix/volume/pan) is even read (GranularNode.cpp). AudioPaulStretchNode::ProcessBlock is the same but stricter - it also requires an audition/self-envelope trigger, and returns silent otherwise (PaulStretchNode.cpp) - before any of its 12 params are read. The sweep's bare rig loads no sample and issues no audition, so every param on both nodes is unreachable. Confirm by hand with a real loaded sample.

- known baseline: AUDIOPARAMSWEEPTEST also reports [FAIL] on 10 Spectral Synth params, for four distinct reasons (not one blanket cause - most of its other params pass, since unlike Granular/PaulStretch this node always has a procedurally-generated default spectrogram to render even with nothing connected). rootFreq is only consumed when freqScale=Harmonic (default is Logarithmic) and position only when scanMode=Manual (default is BpmSync) - both gated-by-sibling-default, same class as Audio Filter's gain, just missing a SweepPrerequisitesFor entry that detune/stereoWidth already have (ImageSpectralSynthNode.h/.cpp). glide is voice-retrigger-only (AllocateVoice seeds currentPitchRatio=targetPitchRatio immediately for any freshly-triggered voice, so there is never a stale pitch to glide from - same class as the Oscillator-family glide entry above). detune, ampDecay, ampSustain, ampRelease, scanMode and rate are wired correctly but only manifest over many milliseconds-to-seconds (unison-detune beating, envelope stages after attack completes, playhead advance per block being a small fraction of image width) - none change the single next block Check B measures, the same structural class as Dynamics' knee/rmsWindow/lookahead. fine is the 10th: read live every block into finePitchRatio and applied to both the drone voice and every triggered voice's pitch with no gating (ImageSpectralSynthNode.cpp line ~438) - it is a pure frequency shift on a multi-partial additive tone, which leaves this block's peak+RMS signature essentially unchanged; the same peak/RMS-blind-to-frequency-alone class as the Oscillator/Wave Terrain/Wavetable free-run frequency entries below.

- known baseline: AUDIOPARAMSWEEPTEST also reports [FAIL] on all 8 Arpeggiator params for one shared cause: AudioArpeggiatorNode::ProcessBlock (NoteNodes.cpp) drives its step clock off Transport::Instance().Beats(), but the headless sweep runs before glfwInit()/AudioEngine::Start() and nothing ever calls Transport::Tick(), so Beats() stays frozen at 0 for the whole probe - exactly one step fires (at mLastStep's initial -1 boundary) and never again, so mode/octaves/rateMode/rateBeats/rateSeconds/ gatePercent/stepGates' effect on subsequent steps is never observable. Arpeggiator's 8th failing param, useGlobalScale, WAS a genuinely dropped feature (stored via mUseGlobalScale.store in PushParams but never loaded/read anywhere in ProcessBlock) - fixed directly in NoteNodes.cpp: the gated step-trigger branch now snaps seqNote[idx] through MusicTime::SnapToScale before pushing the note-on, same call as Note Filter/Note Transpose below. It still reports [FAIL] after the fix, for the same reason those two do (see next paragraph) - the sweep's held chord is already diatonic, so the fix is real but unobservable by this rig.

- known baseline: AUDIOPARAMSWEEPTEST also reports [FAIL] on useGlobalScale for Note Filter, Note Transpose and Arpeggiator (unlike Note Stack above, this trio IS a rig blind spot): Transport defaults to key=C/scale=major, and the sweep's probe notes (60/64/67 chord or single note 69) already lie on that scale, so snapping is a no-op whether useGlobalScale is on or off (NoteNodes.cpp's AudioNoteFilterNode/AudioSemitoneShiftNode/ AudioArpeggiatorNode ProcessBlock).

- known baseline: AUDIOPARAMSWEEPTEST also reports [FAIL] on Pitch Bend's bendSemitones. Not a dropped mailbox push - AudioPitchBendNode::ProcessBlock writes it into out.bendSemitones correctly (NoteNodes.cpp). The sweep's note-outbox signature (RunNoteWindow/RunOneBlock in main.cpp) only reads note/velocity/isNoteOn/frameOffset off each NoteEvent - bendSemitones isn't part of either signature, so a param whose only effect is that field is structurally invisible here.

- known baseline: AUDIOPARAMSWEEPTEST also reports [FAIL] on Note Echo's repeats/decay/transposePerRepeat (delayMs itself passes). Residual gap left by RunNoteWindow's earlier fix: the window is 12*256=3072 samples (64ms) at the sweep's 48kHz rig, but delayMs's own 150ms default schedules the first repeat at 7200 samples - outside the window regardless of these three params' value, so only the immediate dry passthrough is ever observed.

- known baseline: AUDIOPARAMSWEEPTEST also reports [FAIL] on Plugin's plugin_accepts_notes (3rd by-design param, alongside bypass/map_slots documented above). mAcceptsNotes is set once from the loaded plugin's own descriptor (AudioPluginNode.cpp) and has no UI control or CookIfNeeded path at all - it's read-only serialized metadata, not a live-settable param.

- known baseline: AUDIOPARAMSWEEPTEST also reports [FAIL] on all seven Audio File params (loop, followTransport, monitor, volume, gain, attack, release - registered type name AudioFileNode, in AnalyzeNodes.h/.cpp). Same root cause as Sampler/Granular/PaulStretch above: AudioFilePlayerAudioNode:: ProcessBlock computes hasBuffer from mActiveBuffer and, with the sweep's bare rig loading no file, gates all audible output behind it - matching AudioFileNode's own "no file loaded" behaviour comment. followTransport additionally only flips Play()/Pause() when Transport::IsPlaying() changes between cooks, which the sweep's single before/after probe never triggers.

- known baseline (Infinite-Turbo nodes): AUDIOPARAMSWEEPTEST reports [FAIL] on every MPC pad param (pad*_mode/volume/pitch/pan/start/end, baseNote, volume, velocitySensitive) and on MPC Out's pad - the rig loads no sample, so no pad ever sounds. Looper: every param except thru (lengthMode, bars, subDivision, syncStart, loop, direction, level, autoLatency, latencyOffsetMs) only acts on a recorded loop, and the rig never presses REC. Super Mixer's trim* (input gain) should pass: it scales the input before the EQ. VMPC (video pads, note input): if a note/param sweep picks it up, every param FAILs by design - it renders no audio and the rig loads no clip. Predictive Notes/Rhythm (ported from upstream, 0.37): most params only act on a learned model and the rig never presses Learn, so FAILs there are expected; upstream's own tests (INFINITE_PREDMIDITEST etc.) are not wired into Turbo yet. Super Mixer's eqMidFreq* is covered by SweepPrerequisitesFor (mid gain set first).

- known baseline (observed 2026-09-25, upstream node, not in the macOS list): Equation Synth fails 9 params - frequency (note-driven, same as Oscillator), ampSustain/ampRelease/filter ADSR (release unreachable without a note-off, sustain later than the probe window, filter envelope gated by its amount), plus preset and knobD, which are not analysed yet.
